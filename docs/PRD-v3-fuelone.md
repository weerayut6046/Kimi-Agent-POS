## 1. บทสรุปผู้บริหาร

### 1.1 ปัญหา

ปั๊มน้ำมันอิสระและเชนขนาดกลางในไทยส่วนใหญ่ยังใช้ระบบที่แยกส่วนกันอยู่ 3–4 ระบบ ได้แก่ เครื่องคิดเงินหน้าร้าน, ระบบควบคุมตู้จ่าย (Forecourt Controller) ของผู้ผลิตแต่ละยี่ห้อ, สมุดจดกะด้วยมือ และไฟล์ Excel สำหรับสรุปยอด ผลที่ตามมาคือ

- **กระทบยอดไม่ตรง** — ยอดมิเตอร์ตู้จ่าย ยอดเงินในลิ้นชัก และยอดในระบบไม่ตรงกัน ต้องใช้เวลาไล่หาเฉลี่ยวันละ 45–90 นาทีต่อสาขา
- **ปิดกะช้าและผิดพลาด** — พนักงานคำนวณด้วยมือ เกิดข้อพิพาทเรื่องเงินขาด/เกินเป็นประจำ
- **เจ้าของไม่เห็นภาพรวม** — ต้องรอรายงานรายวันจากแต่ละสาขา ไม่สามารถตัดสินใจเรื่องราคาหรือการสั่งเติมน้ำมันได้ทันเวลา
- **เน็ตล่มแล้วขายไม่ได้** — ระบบ cloud-only ที่มีอยู่ในตลาดหยุดให้บริการทันทีเมื่ออินเทอร์เน็ตขาด ซึ่งเกิดบ่อยในสาขาต่างจังหวัด
- **ภาระเอกสารตามกฎหมาย** — การจัดทำรายงาน ธพ.น. ส่งกรมธุรกิจพลังงาน และ e-Tax Invoice ยังทำแยกจากระบบขาย

### 1.2 ทางออก

ระบบ POS ครบวงจรที่ทำงานบนโค้ด UI ชุดเดียวแต่รันได้ทุกแพลตฟอร์ม (Windows / macOS / Linux / iOS / Android / เบราว์เซอร์) โดยมี **Station Edge Server** ประจำสาขาเป็นแกนกลาง ทำให้ระบบขายต่อได้ 100% แม้อินเทอร์เน็ตขาด และเชื่อมตู้จ่ายกับเกจวัดถังโดยตรงเพื่อกระทบยอดอัตโนมัติ

## 2. เป้าหมายและตัวชี้วัด

### 2.1 เป้าหมายผลิตภัณฑ์

| #   | เป้าหมาย                | ตัวชี้วัด                           | เกณฑ์                         |
| --- | ----------------------- | ----------------------------------- | ----------------------------- |
| G1  | ปิดกะได้เร็วและแม่นยำ   | เวลาเฉลี่ยในการปิดกะ                | ≤ 5 นาที (จากเดิม 45–90 นาที) |
| G2  | กระทบยอดน้ำมันอัตโนมัติ | ส่วนต่าง wet stock ที่ไม่มีคำอธิบาย | ≤ 0.3% ของปริมาณจ่ายรายวัน    |
| G3  | ขายต่อได้เมื่อเน็ตขาด   | อัตราธุรกรรมสำเร็จช่วงออฟไลน์       | 100%                          |
| G4  | ปิดการขายน้ำมันเร็ว     | จำนวนการแตะจนจบรายการเงินสด         | ≤ 3 ครั้ง                     |
| G5  | เจ้าของเห็นยอดทันเวลา   | ความล่าช้าของยอดบน Dashboard        | ≤ 60 วินาที เมื่อออนไลน์      |

### 2.2 ตัวชี้วัดธุรกิจ

- ระยะเวลาติดตั้งต่อสาขา ≤ 1 วันทำการ
- อัตราการใช้งานต่อเนื่องหลัง 90 วัน ≥ 90% ของสาขาที่ติดตั้ง
- จำนวนตั๋วสนับสนุนต่อสาขาต่อเดือน ≤ 1.5 ใบ ภายในเดือนที่ 3

### 2.3 ตัวชี้วัดคุณภาพ

- ระบบขายที่สาขาพร้อมใช้งาน ≥ 99.95% (นับเฉพาะ Station Edge)
- เวลาตอบสนองของหน้าจอลานจ่าย p95 ≤ 150 ms
- ธุรกรรมที่ซิงก์ขึ้น cloud สำเร็จ ≥ 99.99% ภายใน 24 ชม.

## 4. ผู้ใช้และ Persona

### P1 — พนักงานแคชเชียร์ (ผู้ใช้หลัก)

อายุ 20–45 ปี ทำงานกะละ 8–12 ชม. ทักษะคอมพิวเตอร์พื้นฐาน มักทำงานคนเดียวในตู้แคชเชียร์ตอนกลางคืน สลับระหว่างรับเงินหน้าลานกับขายของหน้าร้านตลอดเวลา

**ต้องการ:** ปิดบิลเร็ว ไม่ต้องคิดเลข ไม่ต้องจำรหัส
**กลัว:** เงินขาดตอนปิดกะแล้วต้องชดใช้

### P2 — เด็กปั๊ม/พนักงานลาน

รับออเดอร์ที่หน้ารถ ถือแท็บเล็ตหรือมือถือ ต้องการยืนยันชนิดน้ำมันและจำนวนเงินให้แคชเชียร์รู้ก่อนรถมาถึงตู้

**ต้องการ:** ปุ่มใหญ่ กดง่ายกลางแดด สวมถุงมือได้

### P3 — ผู้จัดการสาขา

ดูแล 1 สาขา รับผิดชอบการปิดกะ อนุมัติการยกเลิกบิล สั่งเติมน้ำมัน

**ต้องการ:** เห็นความผิดปกติทันที (เงินขาด, ส่วนต่างถัง, การยกเลิกบิลผิดปกติ)

### P4 — เจ้าของ/ผู้บริหารหลายสาขา

ไม่อยู่หน้างาน ดูผ่านมือถือเป็นหลัก

**ต้องการ:** ยอดรวมทุกสาขา เปรียบเทียบสาขา แจ้งเตือนเมื่อผิดปกติ

### P5 — เจ้าหน้าที่บัญชี

ปิดบัญชีรายเดือน กระทบยอดบัตรกับ statement ธนาคาร ออกใบกำกับภาษี

**ต้องการ:** ข้อมูลครบถ้วน ส่งออกได้ ตรวจสอบย้อนหลังได้

### P6 — ช่างเทคนิค/ผู้ติดตั้ง

ตั้งค่าตู้จ่าย เกจวัดถัง เครื่องพิมพ์ ในวันติดตั้ง

**ต้องการ:** เครื่องมือทดสอบการเชื่อมต่อ อ่าน log ได้

## 7. ความต้องการที่ไม่ใช่เชิงหน้าที่

### 7.1 ประสิทธิภาพ

| ด้าน                       | เกณฑ์                       |
| -------------------------- | --------------------------- |
| เปิดแอปจนพร้อมขาย          | ≤ 3 วินาที                  |
| ตอบสนองการแตะบนหน้าลานจ่าย | p95 ≤ 150 ms                |
| อัปเดตสถานะหัวจ่าย         | ≤ 1 วินาทีหลังเหตุการณ์จริง |
| ปิดบิลจนพิมพ์ใบเสร็จ       | ≤ 2 วินาที                  |
| โหลดรายงานย้อนหลัง 1 เดือน | ≤ 5 วินาที                  |
| รองรับพร้อมกันต่อสาขา      | 8 เครื่อง POS + 32 หัวจ่าย  |

### 7.2 ความพร้อมใช้งาน

- Station Edge Server: 99.95% (ไม่พึ่งอินเทอร์เน็ต)
- Cloud: 99.9%
- ระบบต้องขายต่อได้เต็มรูปแบบเมื่อขาดอินเทอร์เน็ตต่อเนื่องอย่างน้อย 72 ชั่วโมง
- เมื่อ Station Edge ล่ม เครื่อง POS ต้องเข้าสู่โหมดฉุกเฉิน บันทึกรายการลงเครื่องและแจ้งเตือนชัดเจน

### 7.3 ความปลอดภัย

- เข้ารหัสข้อมูลระหว่างส่ง TLS 1.3 ทุกช่องทาง รวมถึงระหว่าง POS กับ Station Edge บน LAN
- เข้ารหัสข้อมูลที่จัดเก็บ AES-256 ทั้งบน Station Edge และ Cloud
- **ห้ามเก็บหมายเลขบัตรเต็มในทุกส่วนของระบบ** ใช้เฉพาะ token และเลข 4 ตัวท้าย
- แยกเครือข่ายส่วนที่เกี่ยวกับบัตรออกจากเครือข่ายทั่วไปของสาขา
- หมุนเวียนกุญแจเข้ารหัสทุก 90 วัน
- ทุกคำขอไปยัง Cloud ต้องมี token ของอุปกรณ์ที่ผูกกับสาขา

### 7.4 การใช้งาน

- รองรับภาษาไทยและอังกฤษ สลับได้ทันทีโดยไม่ต้องรีสตาร์ท
- ปุ่มกดทุกปุ่มบนหน้าจอขายสูงอย่างน้อย 44 px และปุ่มหลัก 56 px ขึ้นไป
- อ่านได้ในสภาพแสงจ้าใต้แคนโนปี้ (คอนทราสต์ข้อความหลักอย่างน้อย 7:1)
- โหมดมืดเป็นค่าตั้งต้นสำหรับหน้าจอขาย เนื่องจากปั๊มส่วนใหญ่เปิด 24 ชั่วโมง
- ใช้งานได้ด้วยแป้นพิมพ์ล้วนสำหรับผู้ใช้ที่ชำนาญ (ปุ่มลัดทุกฟังก์ชันหลัก)
- รองรับ prefers-reduced-motion

### 7.5 การขยายระบบ

- รองรับ 500 สาขา และ 50 ล้านธุรกรรมต่อปี บนสถาปัตยกรรมเดิม
- เพิ่มสาขาใหม่ไม่กระทบสาขาเดิม
- ข้อมูลแยกตาม tenant ระดับฐานข้อมูล

## 8. สถาปัตยกรรมระบบ

### 8.1 ภาพรวม 3 ชั้น

```text
┌─────────────────────────────────────────────────────────┐
│  ชั้นที่ 1 — CLIENT (โค้ด UI ชุดเดียว)                    │
│  React + TypeScript + Vite                              │
│   ├─ Tauri v2      → Windows / macOS / Linux (POS)      │
│   ├─ Capacitor     → iOS / Android (ลาน, ผู้บริหาร)      │
│   └─ PWA           → เบราว์เซอร์ (หลังบ้าน, Dashboard)   │
└────────────────────────┬────────────────────────────────┘
                         │ LAN · REST + WebSocket · TLS
┌────────────────────────▼────────────────────────────────┐
│  ชั้นที่ 2 — STATION EDGE SERVER (mini PC ประจำสาขา)      │
│  Go (แนะนำ) หรือ NestJS + PostgreSQL local              │
│   ├─ Forecourt Driver  (IFSF / Tokheim / Wayne / Gilbarco)│
│   ├─ ATG Driver        (Veeder-Root TLS-350/450)         │
│   ├─ Peripheral Driver (พิมพ์ / ลิ้นชัก / สแกน / EDC)     │
│   ├─ Transaction Engine + Outbox                         │
│   └─ Sync Agent                                          │
│  ── เป็น source of truth ของสาขา ──                      │
└────────────────────────┬────────────────────────────────┘
                         │ Internet · mTLS · ซิงก์ทางเดียวเป็นหลัก
┌────────────────────────▼────────────────────────────────┐
│  ชั้นที่ 3 — CLOUD (multi-tenant)                        │
│  API Gateway → บริการหลัก (Go/NestJS)                    │
│  PostgreSQL + TimescaleDB · Redis · S3                   │
│  ระบบวิเคราะห์ · แจ้งเตือน · e-Tax · รายงานราชการ         │
└─────────────────────────────────────────────────────────┘
```

### 8.2 เหตุผลของ Station Edge Server

นี่คือการตัดสินใจทางสถาปัตยกรรมที่สำคัญที่สุดของโครงการ

1. **เบราว์เซอร์คุยกับตู้จ่ายไม่ได้** — ตู้จ่ายสื่อสารผ่าน RS-485, Current Loop หรือ TCP ด้วยโปรโตคอลเฉพาะของผู้ผลิต ต้องมีบริการที่รันบนเครื่องในสาขาเป็นตัวแปลง
2. **ต้องมีศูนย์กลางในสาขา** — เมื่อมีเครื่อง POS หลายเครื่อง ต้องมีจุดเดียวที่รู้ว่าหัวจ่ายไหนถูกจองโดยเครื่องไหน มิฉะนั้นจะเก็บเงินซ้ำ
3. **ทนเน็ตขาด** — เมื่อ Station Edge เป็น source of truth ของสาขา อินเทอร์เน็ตกลายเป็นแค่ช่องทางส่งข้อมูลออก ไม่ใช่เส้นเลือดหลัก
4. **ลดภาระ Cloud** — ข้อมูลระดับวินาทีจากตู้จ่ายและเกจถูกย่อยที่สาขาก่อน ส่งขึ้น Cloud เฉพาะที่จำเป็น

**ข้อเสียที่ยอมรับ:** ต้องมีฮาร์ดแวร์เพิ่มต่อสาขา (mini PC ประมาณ 8,000–15,000 บาท) และต้องมีกลไกอัปเดตซอฟต์แวร์จากระยะไกล

### 8.3 ทางเลือกภาษาสำหรับ Station Edge

| ประเด็น                 | Go                                         | NestJS (Node)                                |
| ----------------------- | ------------------------------------------ | -------------------------------------------- |
| การติดตั้ง              | binary เดียว ไม่ต้องลง runtime             | ต้องลง Node.js และ dependency                |
| การจัดการ serial/TCP    | เสถียรกว่า ควบคุม goroutine ต่อพอร์ตได้ชัด | ต้องพึ่ง native module ที่แตกง่ายเวลาอัปเกรด |
| การใช้หน่วยความจำ       | ~40 MB                                     | ~180 MB                                      |
| ใช้โค้ดร่วมกับ frontend | ไม่ได้                                     | ได้ (TypeScript ทั้งหมด)                     |
| ความเร็วในการพัฒนา      | ช้ากว่าเล็กน้อย                            | เร็วกว่า                                     |

**คำแนะนำ:** ใช้ **Go** สำหรับ Station Edge เนื่องจากต้องติดตั้งบนเครื่องหลายร้อยสาขาที่ไม่มีทีมไอทีดูแล และใช้ **NestJS** สำหรับ Cloud เพื่อแบ่งปัน type กับ frontend

**ทางเลือกสำรอง:** หากทีมมีขนาดเล็กและต้องการความเร็วในการส่งมอบสูงสุด ใช้ NestJS ทั้งสองชั้น แต่ต้องแพ็กด้วย `pkg` หรือ Docker เพื่อลดปัญหาการติดตั้ง

### 8.5 สัญญาการซิงก์ข้อมูล

**หลักการ: สาขาเป็นเจ้าของรายการของตัวเอง (station-authoritative)**

ธุรกรรมการขายเกิดที่สาขาและซิงก์ขึ้น Cloud ทางเดียวเท่านั้น Cloud ไม่มีสิทธิ์แก้ไขธุรกรรมที่สาขาสร้าง ทำให้ความขัดแย้งของข้อมูลเป็นไปไม่ได้โดยการออกแบบ

ส่วนข้อมูลตั้งค่า (ราคา สินค้า ผู้ใช้ ลูกค้าฟลีต) ไหลจาก Cloud ลงสาขาทางเดียว ใช้ระบบเวอร์ชันเป็นตัวกำหนดว่าสาขาได้รับครบหรือยัง

**กลไก Outbox**

1. ทุกธุรกรรมที่ปิดบิลจะเขียนลงตาราง `transactions` และ `outbox_events` ใน transaction เดียวกันของฐานข้อมูล
2. Sync Agent อ่าน `outbox_events` ตามลำดับ ส่งเป็นชุดละไม่เกิน 200 เหตุการณ์
3. ทุกเหตุการณ์มี `idempotency_key = {station_id}:{sequence_no}` Cloud ปฏิเสธเหตุการณ์ซ้ำโดยไม่แจ้งข้อผิดพลาด
4. เมื่อ Cloud ตอบรับ จึงทำเครื่องหมายว่าส่งแล้ว
5. หากส่งไม่สำเร็จ ใช้ exponential backoff เริ่มที่ 5 วินาที สูงสุด 5 นาที
6. เก็บเหตุการณ์ที่ยังไม่ซิงก์ไว้ได้อย่างน้อย 30 วัน

**เลขที่เอกสารตอนออฟไลน์**

แต่ละสาขาได้รับช่วงเลขที่เอกสารล่วงหน้าจาก Cloud (จองครั้งละ 10,000 เลข) เมื่อเหลือน้อยกว่า 2,000 จะขอช่วงใหม่อัตโนมัติ ทำให้ออกเอกสารตอนออฟไลน์ได้โดยเลขไม่ซ้ำและไม่ข้าม

**สถานะที่ผู้ใช้ต้องเห็น**

หน้าจอต้องแสดงสถานะการซิงก์ตลอดเวลา — ออนไลน์ / ออฟไลน์พร้อมจำนวนรายการค้าง / กำลังซิงก์ — เพราะพนักงานต้องรู้ว่าข้อมูลถึงสำนักงานใหญ่แล้วหรือยังก่อนปิดกะ

REST สำหรับงาน CRUD ทั่วไป และ GraphQL สำหรับหน้า Dashboard ที่ต้องดึงข้อมูลหลายมิติพร้อมกัน เพื่อลดจำนวน round-trip บนมือถือ

### 10.4 หลักการร่วม

- ทุก error ตอบด้วยโครงสร้างเดียวกัน `{ code, message, details, trace_id }` โดย `message` เป็นภาษาไทยที่แสดงให้ผู้ใช้ได้ทันที
- ทุกคำขอที่เปลี่ยนแปลงข้อมูลต้องรองรับ idempotency key
- จำกัดอัตราเรียกต่อสาขา และตอบ `429` พร้อม `Retry-After`

## 11. หลักการออกแบบ UX/UI

### 11.1 หลักการนำ

1. **สีต้องมีความหมายเสมอ** — ใช้พื้นหลังน้ำเงินอมดำโทนเดียว แล้วสงวนสีสดไว้ให้ชนิดน้ำมันเท่านั้น ตรงกับแถบสีหัวจ่ายจริงที่พนักงานจำได้อยู่แล้ว ทำให้ระบุชนิดน้ำมันได้โดยไม่ต้องอ่านตัวอักษร
2. **ผังบนจอต้องตรงกับผังจริง** — จัดกลุ่มหัวจ่ายตามเกาะจ่ายจริง ไม่ใช่เรียงเป็นตารางทั่วไป แคชเชียร์จะเทียบจอกับสิ่งที่เห็นนอกหน้าต่างได้ทันที
3. **สถานะที่ต้องลงมือทำต้องเด่นที่สุด** — หัวจ่ายที่ "รอชำระเงิน" ต้องดึงสายตาก่อนอย่างอื่นเสมอ
4. **ออฟไลน์ไม่ใช่ข้อผิดพลาด** — แสดงสถานะการซิงก์เป็นองค์ประกอบปกติของหน้าจอ ไม่ใช่ป๊อปอัปเตือนภัย พนักงานต้องรู้สึกว่าขายต่อได้ตามปกติ
5. **ตัวเลขต้องนิ่ง** — ใช้ tabular figures ทุกจุดที่แสดงตัวเลข เพื่อให้ยอดเงินที่วิ่งขึ้นไม่ขยับซ้ายขวา อ่านง่ายเหมือนหน้าปัดตู้จ่าย

### 11.2 โครงหน้าจอขาย

- **แถบบน** — ชื่อสาขา เครื่อง กะ พนักงาน ยอดกะสะสม เวลา และสถานะซิงก์
- **พื้นที่หลักซ้าย (~62%)** — ผังลานจ่ายแบ่งตามเกาะ ตามด้วยแถบระดับถังใต้ดิน
- **แผงขวา (~38%)** — บิลที่กำลังทำ รายการสินค้าเพิ่ม วิธีชำระเงิน และปุ่มชำระเงินขนาดใหญ่
- **แถบล่าง** — สลับโหมด: ลานจ่าย / หน้าร้าน / สมาชิก-ฟลีต / กะ / รายงาน

บนจอต่ำกว่า 1080 px แผงขวาจะเลื่อนลงมาอยู่ใต้ผังลานจ่าย และผังเปลี่ยนเป็น 2 คอลัมน์

### 11.3 ข้อกำหนดของงานเขียนในอินเทอร์เฟซ

- ใช้คำที่พนักงานปั๊มใช้จริง เช่น "หัวจ่าย" ไม่ใช่ "Nozzle", "รอชำระเงิน" ไม่ใช่ "Pending"
- ปุ่มบอกสิ่งที่จะเกิดขึ้น เช่น "ชำระเงิน ฿1,357.13" ไม่ใช่ "ยืนยัน"
- ข้อความผิดพลาดต้องบอกว่าเกิดอะไรและต้องทำอย่างไร ห้ามขอโทษหรือคลุมเครือ
  - ตัวอย่างที่ถูก: "เชื่อมต่อตู้จ่าย 03 ไม่ได้ — ตรวจสอบสายที่ตู้ควบคุม แล้วกดลองใหม่"
  - ตัวอย่างที่ผิด: "เกิดข้อผิดพลาด กรุณาลองใหม่ภายหลัง"
- หน้าจอว่างต้องชวนให้ลงมือทำ เช่น "ยังไม่มีรายการรอชำระ — แตะหัวจ่ายที่ขึ้นสถานะรอชำระเงิน"

### 11.4 การเข้าถึง

- คอนทราสต์ข้อความหลักอย่างน้อย 7:1, ข้อความรองอย่างน้อย 4.5:1
- ทุกองค์ประกอบที่โฟกัสได้ต้องมีเส้นขอบโฟกัสที่มองเห็นชัด
- ห้ามใช้สีเป็นตัวสื่อความหมายเพียงอย่างเดียว ต้องมีข้อความหรือสัญลักษณ์กำกับเสมอ
- รองรับ `prefers-reduced-motion` โดยปิดแอนิเมชันทั้งหมด

- ห้ามเก็บ PAN เต็ม, CVV, หรือข้อมูลแถบแม่เหล็ก ในทุกกรณี รวมถึงใน log
- แยก VLAN ของเครื่อง EDC ออกจากเครือข่ายทั่วไปของสาขา

## 13. กลยุทธ์การทดสอบ

### 13.1 ระดับการทดสอบ

| ระดับ            | ขอบเขต                                          | เป้าหมายความครอบคลุม |
| ---------------- | ----------------------------------------------- | -------------------- |
| Unit             | ตรรกะการคำนวณเงิน ภาษี ส่วนลด กระทบยอด          | ≥ 90% ในโมดูลการเงิน |
| Integration      | Driver แต่ละยี่ห้อกับตัวจำลอง, API ระหว่างชั้น  | ทุก endpoint         |
| End-to-end       | เส้นทางการขายหลัก 12 เส้นทาง บนทุกแพลตฟอร์ม     | 100% ของเส้นทางหลัก  |
| Hardware-in-loop | ตู้จ่ายจริง เกจจริง เครื่องพิมพ์จริง ในห้องแล็บ | ก่อนปล่อยทุกเวอร์ชัน |
| ทดสอบภาคสนาม     | สาขานำร่อง 2 แห่ง ใช้งานจริง 30 วัน             | ก่อนขยาย             |

### 13.2 สถานการณ์ทดสอบที่ห้ามข้าม

1. ตัดอินเทอร์เน็ตกลางการปิดบิล แล้วต้องขายต่อได้และไม่มีข้อมูลสูญหาย
2. ตัดไฟ Station Edge กลางการจ่ายน้ำมัน แล้วเปิดใหม่ ต้องกู้รายการค้างชำระได้ครบ
3. เครื่อง POS สองเครื่องกดเก็บเงินหัวจ่ายเดียวกันพร้อมกัน ต้องมีเครื่องเดียวที่สำเร็จ
4. เปลี่ยนราคาขณะที่มีหัวจ่ายกำลังจ่ายอยู่ ต้องรอจนจบรายการและใช้ราคาเดิมกับรายการนั้น
5. ซิงก์ข้อมูลค้าง 3,000 รายการหลังเน็ตกลับมา ต้องไม่ทำให้หน้าจอขายหน่วง
6. ส่งเหตุการณ์เดิมซ้ำ 3 ครั้ง Cloud ต้องบันทึกเพียงครั้งเดียว
7. เลขที่เอกสารต้องไม่ซ้ำและไม่ข้าม แม้สร้างตอนออฟไลน์ข้ามวัน
8. ปิดกะขณะยังมีหัวจ่ายค้างชำระ ต้องบล็อกและระบุว่าค้างที่หัวไหน
9. ตู้จ่ายส่งข้อมูลผิดรูปแบบ ระบบต้องไม่ล่มและบันทึก log
10. ระดับถังลดลงผิดปกติโดยไม่มีการจ่าย ต้องแจ้งเตือนภายใน 15 นาที

### 13.3 เกณฑ์การยอมรับเพื่อออกเวอร์ชัน

- ไม่มีข้อบกพร่องระดับวิกฤตหรือสูงค้างอยู่
- ทดสอบ hardware-in-loop ผ่านครบทุกยี่ห้อที่ประกาศรองรับ
- ทดสอบภาระงานผ่านที่ 2 เท่าของปริมาณสูงสุดที่คาดไว้
- ทดสอบการกู้คืนจากการสำรองข้อมูลสำเร็จภายใน 4 ชั่วโมง
