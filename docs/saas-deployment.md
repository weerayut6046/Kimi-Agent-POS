# แยกระบบ SaaS และระบบกิจการ

รุ่นนี้ใช้ **ชุดติดตั้งและฐานข้อมูลแยกต่อกิจการ** โดยโหมดใช้งานจริงใช้ Supabase Auth ของแต่ละกิจการ ส่วนบริหาร SaaS เก็บเพียงทะเบียนกิจการและลิงก์เข้าใช้งาน ไม่รวมบิล สมาชิก พนักงาน หรือข้อมูลการเงินของลูกค้าไว้ในฐานเดียวกัน

## พื้นที่ทำงาน

| รูปแบบระบบ | ผู้ใช้                    | พื้นที่ทำงาน                                 |
| ---------- | ------------------------- | -------------------------------------------- |
| `platform` | ผู้ดูแลแพลตฟอร์ม          | `/platform` ทะเบียนกิจการและข้อมูลติดต่อ     |
| `business` | เจ้าของกิจการ / ผู้จัดการ | หลังบ้านกิจการ สาขา พนักงาน สินค้า และรายงาน |
| `business` | พนักงาน                   | หน้าขาย เปิด–ปิดกะ และประวัติขาย             |

บัญชี `admin` ของแต่ละชุดติดตั้งเป็นคนละบัญชีใน Auth และฐานข้อมูลคนละชุด ไม่มีการเชื่อมสิทธิ์ข้ามกิจการ ผู้ดูแลระบบเดิมยังมีสิทธิ์ครบภายในชุดติดตั้งเดิม ส่วนเมนูหน้าขายและหลังบ้านเป็นการจัดกลุ่มงานตามสิทธิ์เดิม ไม่ได้ลดสิทธิ์พนักงาน

## ตั้งค่าชุดติดตั้ง

ค่าฝั่งเซิร์ฟเวอร์ `PUMPPOS_DEPLOYMENT_MODE` เป็นตัวกำหนดขอบเขต API ไม่อ่านรูปแบบระบบจาก header, query, browser storage หรือข้อมูลที่ลูกค้าส่งมา

```dotenv
# เซิร์ฟเวอร์ส่วนกลาง ใช้ Supabase project ของแพลตฟอร์มเท่านั้น
PUMPPOS_DEPLOYMENT_MODE=platform
```

```dotenv
# เซิร์ฟเวอร์ของกิจการหนึ่งราย ใช้ฐานของกิจการนั้นและ Supabase Auth ใน production
PUMPPOS_DEPLOYMENT_MODE=business
```

เมื่อไม่ได้ตั้งค่า ระบบใช้ `business` เพื่อรองรับชุดติดตั้งเดิม ค่าอื่นนอกเหนือสองค่านี้จะทำให้การตรวจขอบเขต API ล้มเหลว ไม่สลับรูปแบบให้เอง

ฐานของกิจการเลือกได้ระหว่าง Supabase PostgreSQL กับ PostgreSQL ในเครื่อง แต่โหมด production ยังใช้ Supabase Auth สำหรับบัญชีและ session กำหนด Database URL, Supabase Auth URL/keys, APP_SECRET และ frontend Supabase URL ให้ตรงกับชุดติดตั้งนั้น ค่า secret ห้ามใช้ร่วมข้ามกิจการหรือใส่ใน frontend ส่วน hostname ของเว็บต้องแยกกันเพื่อแยก session และ browser cache ด้วย

ใช้โค้ดรุ่นเดียวกันและ migration ชุดเดียวกันได้ แต่ต้องรัน migration ในฐานปลายทางของแต่ละชุดอย่างแยกกัน ตาม workflow เดิมใน README และ `docs/supabase-backend-migration.md` ไม่ตั้ง `platform` บนฐานที่ยังมีข้อมูลกิจการลูกค้าอยู่

สำหรับชุดติดตั้งใหม่ ใช้ [`npm run setup:system`](./system-installation.md) เตรียมฐานและค่าการเชื่อมต่อ แล้วเปิด `/setup` เพื่อสร้างเจ้าของโดยไม่ต้องล็อกอินก่อน ใน production ต้องใช้รหัสติดตั้งส่วนตัวและลงทะเบียนใบหน้า ชุดที่มีเจ้าของหรือข้อมูลกิจการอยู่แล้วเข้าสู่ระบบตามปกติ ไม่เปิดให้สร้างเจ้าของซ้ำ ระบบไม่สร้าง Supabase project หรือ deploy ให้โดยอัตโนมัติ และไม่มีบัญชีหรือ PIN ตัวอย่างใน production

## ขอบเขตฝั่งเซิร์ฟเวอร์

- `business` ปฏิเสธทุก procedure ใต้ `platform.*` แม้ผู้เรียกเป็น admin
- `platform` เปิดเฉพาะ procedure บริหาร SaaS และรายการ Auth ที่ระบุไว้ งานใหม่ฝั่งกิจการจะถูกปฏิเสธโดยอัตโนมัติ
- บัญชี manager/cashier เข้า API ที่ต้องเข้าสู่ระบบของ platform ไม่ได้
- HTTP รับเงินเข้า, Realtime ของ POS และ scheduled backup ของกิจการถูกปิดใน platform
- `/loyalty` และการโหลด theme/ข้อมูลกะจะไม่ทำงานในหน้าบริหาร platform
- permission `platform` ลงทะเบียนใน `web/contracts/menuPermissions.ts` และตรวจทั้ง route และ server procedure ผู้ดูแลยังได้รับ permission ทั้งหมดตามกติกาเดิม

## ลงทะเบียนกิจการ

เพิ่มกิจการจาก `/platform` โดยระบุรหัส ชื่อ ผู้ติดต่อ origin ของเว็บ และ Supabase project reference ของกิจการ ฐานข้อมูลบังคับไม่ให้รหัส URL และ project reference ซ้ำกัน API ปฏิเสธ project ของแพลตฟอร์มเองและ URL ที่มี credentials, query, fragment หรือ path ที่ไม่ใช่ origin

การลงทะเบียนเป็น **ทะเบียนสำหรับทีมงาน** สถานะ active/paused หมายถึงสถานะทะเบียนเท่านั้น ไม่สร้าง project ไม่เปลี่ยนรหัสผ่าน และไม่ระงับ POS ของกิจการที่อยู่คนละชุดติดตั้ง ปุ่มเปิดระบบกิจการเปิดเว็บของกิจการ ซึ่งจะแสดง `/setup` เฉพาะชุดใหม่ที่ยังไม่มีเจ้าของ มิฉะนั้นให้เข้าสู่ระบบด้วยบัญชีของกิจการนั้น

## ตรวจแผนการติดตั้งก่อนนำขึ้นระบบ

สร้าง JSON ที่ไม่มี secrets ตามตัวอย่าง:

```json
{
  "platform": {
    "appUrl": "https://admin.example.com",
    "supabaseProjectRef": "aaaaaaaaaaaaaaaaaaaa"
  },
  "businesses": [
    {
      "code": "STATION_A",
      "appUrl": "https://station-a.example.com",
      "supabaseProjectRef": "bbbbbbbbbbbbbbbbbbbb"
    }
  ]
}
```

รัน `node ops/validate-saas-deployment.mjs --manifest <path>` เครื่องมือจะตรวจ project และ web origin ว่าไม่ใช้ร่วมกัน รวมถึงข้อมูลและรหัสกิจการที่ซ้ำ โดยไม่เชื่อมบริการจริง สำหรับการทดสอบ localhost ใช้ `--allow-localhost` เพิ่ม

การผ่านตัวตรวจเป็นการตรวจแผนที่ระบุใน JSON เท่านั้น ต้องตรวจ configuration จริงของแต่ละ deployment ให้ตรงกับแผนด้วย

## Desktop และการสำรองข้อมูล

Desktop แต่ละเครื่องผูกกับ origin ของกิจการหนึ่งราย ต้องซิงก์บิลของปลายทางเดิมให้หมดก่อนเปลี่ยนปลายทาง บิลค้างและ cache ห้ามถูกส่งหรือใช้กับอีกกิจการหนึ่ง ไฟล์กู้ภัยต้องนำกลับเข้าระบบปลายทางเดิม

ก่อนอัปเกรด Desktop รุ่นที่ยังไม่เก็บ origin ให้ซิงก์บิลค้างด้วยรุ่นเดิมจนหมดก่อน รุ่นใหม่จะไม่ผูกบิลเก่าที่ไม่ทราบต้นทางให้เอง หากยังมีบิลค้างจะเก็บข้อมูลไว้และหยุดการซิงก์ พร้อมเปิดให้ส่งออกไฟล์กู้ภัยเพื่อตรวจสอบต้นทางกับทีมดูแล ห้ามแก้ origin ของไฟล์กู้ภัยเพื่อส่งเข้ากิจการอื่น

ต้องเก็บ origin เดิมไว้สำหรับกิจการเดิม ไม่ย้าย URL เดิมไปชี้ฐานข้อมูลของอีกกิจการ เพราะการผูก origin ไม่สามารถตรวจการเปลี่ยนฐานข้อมูลเบื้องหลัง URL เดิมได้ หลังอัปเกรดต้องเปิดออนไลน์อย่างน้อยหนึ่งครั้งเพื่อรับผลตรวจรูปแบบระบบที่ Desktop จะเก็บใน cache ก่อนใช้งานออฟไลน์

ไฟล์ `.posbackup` เดิมสำรองทั้งฐานธุรกิจ จึงใช้ได้ภายในกิจการที่มีฐานเฉพาะของตนเท่านั้น ห้ามนำไฟล์ต่างกิจการมากู้คืนทับกัน สำรอง Auth, Storage, configuration และทดสอบกู้คืนตามเอกสารเดิมควบคู่กัน

## งานระยะถัดไป

หลังสร้างเจ้าของ ผู้ดูแลใช้ `/setup` ตั้งข้อมูลและตรวจความพร้อมก่อนเริ่มขายได้ ดู [คู่มือตั้งค่ากิจการ](./business-setup.md)

ระบบสมัครกิจการด้วยตนเอง การ provision project อัตโนมัติ แพ็กเกจ ทดลองใช้ ใบเรียกเก็บค่าบริการ และการต่ออายุยังต้องพัฒนาแยกจาก POS payment ก่อนเปิดบริการแบบสมัครเอง ระบบฐานข้อมูลร่วมหลายกิจการยังไม่ได้เปิดใช้ในรุ่นนี้
