# เข้าสู่ระบบด้วย passkey บนเว็บ

พนักงานเข้าสู่ระบบครั้งแรกด้วย **ชื่อผู้ใช้, PIN และการสแกนใบหน้า** ตามเดิม หลังยืนยันสำเร็จ เว็บจะเสนอให้บันทึก passkey ของ PumpPOS สำหรับการเข้าใช้ครั้งถัดไป พนักงานเลือกบันทึกหรือข้ามได้

เมื่อกลับมาเปิดเว็บ พนักงานที่บันทึก passkey แล้วกด **ยืนยันตัวตนด้วยอุปกรณ์** และปลดล็อกตามวิธีที่อุปกรณ์รองรับ ระบบ POS ตรวจหลักฐาน WebAuthn กับกุญแจสาธารณะที่เก็บในฐานข้อมูล แล้วตรวจสถานะบัญชีและสิทธิ์เข้าสาขาก่อนออกเซสชันใหม่ จึงไม่ต้องกรอกชื่อผู้ใช้หรือ PIN และไม่ต้องเปิดกล้องของเว็บในรอบนั้น หากใช้ passkey ไม่ได้ ยังเข้าสู่ระบบด้วยชื่อผู้ใช้, PIN และใบหน้าได้

Passkey นี้เป็นของ **PumpPOS** และตรวจโดย API ของ PumpPOS ผ่าน SimpleWebAuthn ไม่ใช่ passkey ของ Supabase Auth จึงไม่ต้องเปิดฟีเจอร์ Passkeys ใน Supabase Dashboard หลัง API ตรวจ passkey สำเร็จ ระบบยังออกเซสชัน Supabase Auth สำหรับการเรียก API ของ POS ตามปกติ

## ตั้งค่าก่อนใช้งาน

1. ใช้ขั้นตอน migration ของโครงการกับไฟล์ [`supabase/migrations/20260926001144_passkey_credentials.sql`](../supabase/migrations/20260926001144_passkey_credentials.sql) ก่อนเผยแพร่โค้ดส่วน passkey ตรวจ migration history และทดสอบใน staging ก่อนใช้ `npx supabase db push` ใน release workflow ตาม [คู่มือโครงการ](../README.md) สำหรับฐานข้อมูล local/self-hosted มี migration คู่กันใน [`0031`](../web/db/migrations-postgres/0031_illegal_omega_sentinel.sql) และ [`0032`](../web/db/migrations-postgres/0032_marvelous_salo.sql) ไฟล์เหล่านี้เพิ่มรหัสผู้ใช้ WebAuthn และตารางเก็บกุญแจสาธารณะกับคำท้าทายชั่วคราว โดยไม่เปิดตารางเหล่านี้ให้เบราว์เซอร์อ่านหรือเขียนตรง
2. ตั้งค่าตัวแปรฝั่งเซิร์ฟเวอร์ในสภาพแวดล้อมที่รัน API โดยใช้โดเมนเว็บปัจจุบันของโครงการ:

   ```env
   PUMPPOS_PASSKEY_RP_ID=kimi-agent-pos.vercel.app
   PUMPPOS_PASSKEY_ORIGIN=https://kimi-agent-pos.vercel.app
   ```

   `PUMPPOS_PASSKEY_RP_ID` เป็นชื่อโดเมนอย่างเดียว ไม่มี `https://`, path หรือพอร์ต ส่วน `PUMPPOS_PASSKEY_ORIGIN` เป็น origin แบบ HTTPS ที่ตรงกับเว็บ ไม่มี path หรือ `/` ท้าย URL ทั้งสองค่าต้องตั้งให้สอดคล้องกัน หากเปลี่ยนไปใช้ custom domain ให้เปลี่ยนทั้งสองค่าก่อนลงทะเบียน passkey หากไม่ได้ตั้งหรือค่าไม่ถูกต้อง ระบบจะไม่เสนอการลงทะเบียน passkey และเริ่มยืนยันด้วย passkey ไม่ได้ อย่าใช้ชื่อตัวแปรขึ้นต้น `VITE_` เพราะค่านี้เป็นการตั้งค่าฝั่งเซิร์ฟเวอร์

3. ให้พนักงานที่ต้องบันทึก passkey มีสิทธิ์เมนู **ตั้งค่าระบบ** (`settings`) การเริ่มและจบการลงทะเบียนตรวจสิทธิ์นี้ที่ API ด้วย โดยค่าเริ่มต้นของบทบาทมีสิทธิ์ดังกล่าว แต่ถ้าถูกปิดในสิทธิ์รายบุคคลหรือกลุ่ม พนักงานจะไม่เห็นขั้นตอนบันทึก passkey การเข้าสู่ระบบด้วย passkey ที่ลงทะเบียนไว้แล้วไม่ต้องใช้สิทธิ์เมนูนี้
4. ทดสอบบนเว็บ HTTPS ของโดเมนที่กำหนด: ลงชื่อเข้าใช้ด้วย PIN และใบหน้า → กดบันทึก passkey → ปิดแท็บแล้วเปิดเว็บอีกครั้ง → กดยืนยันตัวตนด้วยอุปกรณ์ → ตรวจว่าเข้าสู่บัญชีและสาขาที่ได้รับสิทธิ์โดยไม่กรอก PIN

ตั้ง Relying Party ID ให้คงที่ก่อนเริ่มใช้งานจริง เพราะ passkey เดิมผูกกับ ID นี้ หากเปลี่ยน Relying Party ID ภายหลังต้องให้พนักงานลงทะเบียน passkey ใหม่

## แก้ปัญหาล็อกอินหลังอัปเดตโค้ด

หากการเข้าสู่ระบบด้วยชื่อผู้ใช้และ PIN ล้มเหลวจากคอลัมน์ `passkey_user_handle` ที่ยังไม่มี แสดงว่าโค้ดใหม่เริ่มทำงานก่อนฐานข้อมูลได้รับ migration การอ่านบัญชีผู้ใช้ต้องใช้คอลัมน์นี้แม้ยังไม่ได้ตั้งค่า passkey

ตรวจฐานข้อมูลที่ API เชื่อมต่อจริง โหมดพัฒนาก็อาจเชื่อมกับ Supabase ที่ใช้งานอยู่ได้ สำหรับ Supabase ให้สำรองข้อมูล ตรวจ `npx supabase db push --linked --dry-run --skip-vault` และใช้ release workflow เพื่อรัน migration `20260926001144_passkey_credentials.sql` สำหรับฐานข้อมูล local/self-hosted ใช้ migration Drizzle `0031` และ `0032` ตาม workflow ของโครงการ ห้ามรันทั้งสองชุดซ้ำบนฐานข้อมูลเดียวกัน

หลังอัปเดต ตรวจว่าประวัติ migration ตรงกัน คอลัมน์และตาราง passkey มีครบ แล้วรีเฟรชหน้าล็อกอิน ไม่ต้องสร้างบัญชีหรือตั้ง PIN ใหม่

## ย้ายจากระบบ passkey เดิม

Passkey ที่เคยลงทะเบียนผ่าน **Supabase Auth Passkeys** ไม่สามารถย้ายกุญแจมาเป็น passkey ของ PumpPOS ได้ พนักงานต้องเข้าสู่ระบบด้วยชื่อผู้ใช้, PIN และใบหน้าอีกครั้ง แล้วบันทึก passkey ใหม่หลังปรับระบบและรัน migration แล้ว ไม่ต้องสร้างบัญชีพนักงานใหม่

หากอุปกรณ์ไม่มี passkey ที่ใช้ได้, ยกเลิกหน้าต่างยืนยัน, หรือเบราว์เซอร์ไม่รองรับ ให้ใช้ขั้นตอน PIN และใบหน้าตามเดิม จากนั้นจึงลองบันทึก passkey ใหม่บนอุปกรณ์ที่ต้องการ

## ขอบเขตและข้อจำกัด

- รองรับเว็บที่ให้บริการผ่าน HTTPS บนโดเมนที่ตั้งค่าไว้เท่านั้น แอป Electron แบบออฟไลน์เปิดหน้าจอจาก `http://127.0.0.1` จึงยังใช้ PIN และการสแกนใบหน้าตามเดิม ส่วนแอปมือถือ Flutter มีขั้นตอนล็อกอินด้วยชื่อผู้ใช้และรหัสผ่านแยกต่างหาก
- WebAuthn บังคับให้ **อุปกรณ์ยืนยันตัวผู้ใช้** ได้ แต่เว็บเลือกวิธีปลดล็อกแทนอุปกรณ์ไม่ได้ อุปกรณ์อาจใช้ใบหน้า, ลายนิ้วมือ, PIN หรือรหัสผ่านของเครื่อง จึงไม่สามารถรับประกันว่าแต่ละครั้งจะสแกนใบหน้าโดยเฉพาะ
- Passkey บางชนิดซิงก์ผ่านบัญชีของระบบปฏิบัติการไปยังอุปกรณ์อื่นได้ การบันทึก passkey จึงไม่ได้รับประกันว่าจะใช้งานได้เฉพาะเครื่องเดิม
