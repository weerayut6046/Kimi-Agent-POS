# PRD v3.0 (FuelOne) เทียบกับระบบที่มีอยู่จริง — Gap Analysis

> อ้างอิงเอกสารเป้าหมาย: [`docs/PRD-v3-fuelone.md`](./PRD-v3-fuelone.md)
> อ้างอิงสถานะปัจจุบัน: [`PRD.md`](../PRD.md) และโค้ดบน branch `claude/fuelone-pos-prd-v3-q40fev` (source `2.1.9`)
> วันที่ตรวจ: สิงหาคม 2569

เอกสารนี้ตอบคำถามเดียวคือ **"ของที่มีอยู่แล้วครอบคลุม PRD v3 ไปเท่าไร และช่องว่างที่เหลือคืออะไรบ้าง"** ทุกข้อความในตารางตรวจกับไฟล์จริง ไม่ได้อ้างจากเอกสารเก่า

## สรุปผู้บริหาร

ระบบปัจจุบัน (PumpPOS `2.1.9`) ครอบคลุม PRD v3 ได้มากกว่าที่ชื่อเวอร์ชันบอก โดยเฉพาะงานหลังการขาย ได้แก่ กะและการกระทบยอดเงิน สต๊อกน้ำมัน ลูกหนี้ ใบกำกับภาษี รายงาน สิทธิ์รายเมนู และ Audit log ส่วนที่ยังขาดเกือบทั้งหมดกระจุกอยู่ที่ **จุดเชื่อมกับฮาร์ดแวร์หน้าลาน** และ **ผลที่ตามมาจากการไม่มีฮาร์ดแวร์นั้น**

ช่องว่างเรียงตามผลกระทบ:

1. **ไม่มีชั้น Station Edge และไม่มี driver ตู้จ่าย** — M1 ทั้งโมดูลจึงยังไม่มี ระบบวันนี้รับเลขมิเตอร์จากคนกรอก (ช่วยด้วย OCR) ไม่ใช่จากตู้ ทำให้ M4-02, M7-03, M7-04 และ §12.4 "ห้ามแก้เลขมิเตอร์ด้วยมือ" ยังทำไม่ได้ตามเจตนา
2. **ไม่มีการอ่านถังอัตโนมัติ (ATG)** — `tank_readings` วันนี้เป็นค่าที่พนักงานวัดเอง ไม่มีอุณหภูมิและระดับน้ำ M6-01/03/06/07 จึงยังเปิดอยู่
3. **การชำระเงินเป็นวิธีเดียวต่อบิล** — `sales.payment_method` เป็น enum เดี่ยว M3-06 (ชำระผสม) ต้องเปลี่ยน schema ไม่ใช่เพิ่ม UI
4. **เลขที่เอกสารออฟไลน์ยังไม่อยู่ในชุดเดียวกับออนไลน์** — ตรงตาม "ไม่ซ้ำ" แต่ยังไม่ตรงตาม "เรียงต่อเนื่อง" ของ M10-05
5. **ลูกค้าองค์กรยังไม่มีระดับ "คันรถ"** — `customers` มี `vehicle_plate` ช่องเดียวและวงเงินก้อนเดียว M5-01/02/03 ต้องมีตารางใหม่

สิ่งที่ **ไม่ควรทำ** คือรื้อระบบเดิมไปเป็น Go + Tauri ตามข้อ 8.3/8.4 ของ PRD ทันที เพราะช่องว่างจริงไม่ได้อยู่ที่ภาษาหรือ shell ของแอป แต่อยู่ที่ยังไม่มีตัวกลางคุยกับฮาร์ดแวร์ ข้อเสนอเรื่องลำดับงานอยู่ท้ายเอกสาร

## 1. ความต้องการเชิงหน้าที่

สถานะ: **มีแล้ว** = ใช้งานได้ตรงตามข้อกำหนด · **บางส่วน** = มีของใกล้เคียงแต่ยังไม่ครบเจตนา · **ยังไม่มี**

## 4. ข้อเสนอลำดับงาน

PRD เสนอสถาปัตยกรรมปลายทางไว้ครบ แต่ไม่ได้บอกว่าจะย้ายจากของที่มีอยู่อย่างไร ข้อเสนอคือ **อย่าเริ่มจากการเปลี่ยนภาษาหรือ shell** เพราะไม่ได้ลดช่องว่างข้อใดเลย ให้เริ่มจากสิ่งที่ปลดล็อกข้ออื่นมากที่สุด

| ลำดับ | งาน                                                              | ปลดล็อก                            | เหตุผล                                                                                             |
| ----- | ---------------------------------------------------------------- | ---------------------------------- | -------------------------------------------------------------------------------------------------- |
| 1     | **ชั้น driver ตู้จ่าย/ATG พร้อมตัวจำลอง**                        | M1 ทั้งหมด, M4-02, M6-01, M7-03/04 | เป็น P0 ของ PRD เอง และเป็นข้อเดียวที่ข้ออื่นรออยู่ ทำเป็นซอฟต์แวร์ล้วนได้ ไม่ต้องรอฮาร์ดแวร์      |
| 2     | สถานะหัวจ่ายและการจองรายการ (claim)                              | M1-01/02/05/07, §13.2 ข้อ 3        | ต่อยอดจากข้อ 1 ทันที และเป็นตรรกะที่ทดสอบได้เต็มที่ก่อนมีฮาร์ดแวร์                                 |
| 3     | แยก `payments` ออกจาก `sales` เป็นหลายแถวต่อบิล                  | M3-06, M3-09, M5-07                | เป็นการเปลี่ยน schema ที่กระทบมากที่สุด ยิ่งทำช้ายิ่งแพง                                           |
| 4     | `effective_at` ในตารางราคา + งานตั้งเวลา                         | M7-02, M7-04                       | เพิ่มคอลัมน์เดียวบนของที่มีอยู่แล้ว ได้ผลตอบแทนสูง                                                 |
| 5     | ตาราง `vehicles` แยกจาก `customers` พร้อมวงเงินและข้อจำกัดรายคัน | M5-01/02/03/04, M1-06              | ปลดล็อกงานฟลีตทั้งกลุ่ม                                                                            |
| 6     | ช่วงเลขที่เอกสารที่จองล่วงหน้าได้                                | M10-05, §8.5                       | ต้องทำก่อนที่ปริมาณบิลออฟไลน์จะมากพอจนย้อนกลับมาแก้ยาก                                             |
| 7     | Station Edge เต็มรูปแบบ                                          | 7.2, §8.5 ทั้งหมด                  | ทำเมื่อข้อ 1–2 พิสูจน์แล้วว่า interface นิ่ง — ถึงตอนนั้นจะเป็นการ "ย้ายที่รัน" ไม่ใช่ "เขียนใหม่" |

เรื่องภาษาของ Station Edge (คำถาม Q1 ของ PRD) ยังไม่ต้องตอบในตอนนี้ ถ้าชั้น driver ถูกออกแบบให้เป็น interface ที่ชัดเจนตั้งแต่ต้น การย้ายไป Go ภายหลังจะเป็นการเขียนใหม่เฉพาะโมดูลนั้น ไม่ใช่ทั้งระบบ

## 5. สิ่งที่ทำไปแล้วในรอบนี้

รอบนี้ทำลำดับที่ 1 และ 2 บางส่วน โดยเป็นซอฟต์แวร์ล้วนที่ทดสอบได้โดยไม่ต้องมีฮาร์ดแวร์:

| ไฟล์                                    | หน้าที่                                                                                                    |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `web/contracts/forecourt.ts`            | นิยามสถานะหัวจ่าย การเปลี่ยนสถานะที่อนุญาต การจองรายการ (claim) และเหตุการณ์จากตู้จ่าย                     |
| `web/api/lib/forecourt/driver.ts`       | interface กลางที่ทุก driver ต้องทำตาม (§8.6) เพื่อเพิ่มยี่ห้อใหม่โดยไม่แตะโค้ดหลัก                         |
| `web/api/lib/forecourt/simulator.ts`    | ตัวจำลองตู้จ่าย — deliverable ของ P0 ใน §14 ใช้พัฒนาและทดสอบโดยไม่ต้องมีตู้จริง                            |
| `web/api/lib/forecourt/atgSimulator.ts` | ตัวจำลองเกจวัดถัง ให้ค่าปริมาตร อุณหภูมิ และระดับน้ำ ตามที่ M6-01 ต้องการ                                  |
| `web/api/lib/forecourt/state.ts`        | ตัวเก็บสถานะลานจ่ายในหน่วยความจำ ทำหน้าที่ "จุดเดียวที่รู้ว่าหัวจ่ายไหนถูกจองโดยเครื่องไหน" ตาม §8.2 ข้อ 2 |

ครอบคลุมสถานการณ์ทดสอบที่ห้ามข้ามใน §13.2 ได้แล้ว 3 ข้อ ได้แก่ ข้อ 3 (สอง POS แย่งหัวจ่ายเดียวกัน), ข้อ 4 (เปลี่ยนราคาขณะกำลังจ่าย) และข้อ 9 (ตู้จ่ายส่งข้อมูลผิดรูปแบบแล้วระบบต้องไม่ล่ม)

ยังไม่ได้ทำในรอบนี้: การเชื่อมชั้นนี้เข้ากับ tRPC และหน้าจอลานจ่ายตาม §11.2 ซึ่งเป็นงานถัดไปที่ชัดเจนที่สุด
